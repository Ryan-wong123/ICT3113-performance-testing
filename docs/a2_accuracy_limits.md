## 1. Golden-set split (commit before anything else)

- Source: `labelling/golden_test_set.csv` (175 tickets).
- Rule (team reading of the brief's "odd rows / even rows"): a ticket whose `row` value is **odd** is in the **tuning set**; a ticket whose `row` value is **even** is in the **test set**. The brief does not say whether "row" means the `row` value or the position in the sorted list; we use the `row` value, so a ticket's set can be read straight from its row number. (Using sorted position instead would give a different test set — only 47 of the 85 test tickets would be the same.)
- Tuning set: design and tune the escalation rule. Test set: every reported accuracy number and every pass/fail decision. Never tune on the test set.
- Caveat to state in the report: all models already ran on the full golden set in Assignment 1, so the test set is not new data; it gives a fair comparison of all configurations on the same tickets with the cascade rule untuned on them.
- Split file: `analysis/a2/golden_split.csv` (`row,final_label,split`), generated by `scripts/split_golden_set.py` from `labelling/golden_test_set.csv`; regenerate or verify with `python3 scripts/split_golden_set.py [--check]`. Unit tests: `tests/test_split_golden_set.py`.

## 3. Pass rule

A configuration passes only if its test-set overall accuracy is at or above the overall limit **and** no category is below its per-category limit. Single models that fail do not need a speed test; the cascade is speed-tested whether or not it passes (marked as not passing if it fails).
